# OCR 选型与性能试验技术存档 · 2026-10-22

## 决策

恢复 **hiroi-sora/RapidOCR-json 的原生 C++ 程序 + ONNX Runtime + PP-OCRv3 中英文检测/识别模型**。点击识别后启动独立进程，结果返回、取消、截图关闭或超时后结束进程。不保留常驻模型，不依赖系统 Python，不下载模型或上传图片。

本机相同输入测试中，这个组合的启动和识别响应均优于 RapidOCRLite a14 + PP-OCRv6 small；Lite + tiny 明显缩小体积并改善速度，但仍未超过原 v3 方案。此决定针对当前 Windows 工具箱、当前硬件和离线按需运行的需求，不代表 v3 在所有机器或所有图片上更好。

## 术语和候选

| 项目/封装 | 推理引擎 | 模型 | 本次定位 |
|---|---|---|---|
| 第三方 RapidOCR-json 原生 EXE | ONNX Runtime，C++ | PP-OCRv3 + mobile 分类器 | 恢复作为产品默认 |
| 官方 RapidOCR 3.10.0，PyInstaller 独立包 | ONNX Runtime 1.23.2，Python API | PP-OCRv6 small + v2.0 mobile 分类器 | 已验证的旧候选，保留文字测试结论 |
| RapidOCRLite 5.0.0a14，C/C++ SDK | 项目专用推理引擎，无 ORT/OpenCV | PP-OCRv6 small / tiny，同一套 ONNX 权重及匹配字典 | 仅离线试验，未接入产品 |

- v6 的尺寸为 tiny / small / medium；mobile 是 v3/v4/v5 常见命名。tiny 不支持日文，small 支持。
- RapidOCR-json、RapidOCR 主线、RapidOCRLite 是不同项目/实现。模型代际不能当成项目版本。
- Lite 仍加载 ONNX 权重，使用专用推理实现；不是另训的仿制模型。`model_type="lite"` 是另一条模型路线，本次未使用。
- 原包 README 标注来源发布包 `RapidOCR-json_v0.2.0.7z`；实际 EXE 横幅是 `RapidOCR-json v1.1.0`。二者均记录，不能混作同一个版本字段。本次从本地旧发布目录逐字节恢复，没有重新下载该发布包；文件 SHA256 是核对依据。

## 环境、输入和方法

- 日期：2026-10-22，Asia/Shanghai；Windows x64，Intel Core i7-3770（4核/8逻辑线程）。Lite SDK 查询 `avx2_compiled=1`、`avx2_active=0`、`active_isa=scalar`。
- 后台有三个 Python 进程持续消耗 CPU；约两秒内各消耗约1.8 CPU秒。复测采集的系统 CPU 忙碌率为62.7%–75.8%。未停止或调优其他工作，因此不是空闲机基准。
- 原始样本是用 Microsoft YaHei 生成的中英文合成图：简单两行、16px小字混排、22行密集文字，以及倾斜、倒置和空白图。不存在用户真实截图样本，不能据此作准确率排名。简单图包含“本地文字识别测试”和“Hello OCR 12345”；小字图包含中文说明、英文工具名称及订单编号/金额；密集图为22行中英文数字混排。
- 公平对比的三张图只在右/底补白到32的倍数，不缩放原始文字，尺寸分别800×416、1216×608、1408×1024。本文仅保留测试条件与结果的文字记录，不附图片、代码、日志或原始数据文件。
- 公平对比中两程序直接读取同一个无透明度 PNG，主要检测参数为 max/4096、不额外补白、thresh=0.3、box_thresh=0.5、unclip=1.6、2×2 dilation。方向分类开启，json 的 mostAngle=0。模型各自要求的归一化、识别宽度和批处理策略保留，不声称数学工作量或内部实现完全相同。
- 推理线程预算均2；Lite图片处理线程2。Lite 的外层识别批次并发仍为其实现默认，因此“2线程”不等于整个进程总共只有两个线程。早期 Lite 默认试验为8线程，不能与后期2线程混称。
- Lite 固定 CPU、默认精确模式 `rec_fast_mode=0`，未启用快速模式、GPU或量化。原生探针用 Windows WIC 解码 PNG，不含 Python；Python仅作为外部进程管理/计时器。
- 时间区分：**启动到首个结果**用父进程墙钟计时、包含依赖/模型/解码/OCR/结果返回；**识别阶段**为初始化后的一次请求，测量边界见各表。各轮测试顺序和重复数见下文。

## 必须保留的计时修正

1. RapidOCR 3.10.0 使用延迟加载。旧 `ocr-worker.py` 在 `RapidOCR()` 构造后输出 ready，此时模型尚未创建；首次 `engine(...)` 才加载检测/分类/识别模型。因此此前把 ready 称“模型加载完成”，或把 ready 后的全部等待称“纯推理”，均不准确。旧的启动到结果总时间仍然有效；旧 ready 后时间只能称“含首次加载的请求时间”。tiny 对比已经显式调用三个模型加载方法，再计识别耗时。
2. 同一原图不一定是同一检测张量：原 v6 short-side min/736 会将800×400图放大至1472×736；Lite默认 max/960 不放大。早期两种配置不能直接作为等输入规模的引擎比较。后期已统一文件及检测尺寸。
3. 不能将 Lite 较慢全部归因于没有 AVX2。scalar 路径、后台争用、线程配置、分辨率、模型计算量和实现都可能影响结果，未分离各自贡献。没有在支持AVX2的新CPU或其他机器上实测。
4. 原生探针加模型的大小不是正式集成后最终安装包大小。压缩SDK、未压缩文件、运行内存和安装程序体积属于不同指标。

## 主要结果：v3 与 Lite small，相同文件

两个回合，每项新进程识别一次；第二回合反转两个引擎的顺序。下表是**从启动到首个结果**的范围，两边边界相同。

| 输入 | RapidOCR-json + v3 | 原生 Lite a14 + v6 small |
|---|---:|---:|
| simple | 0.94–0.97 秒 | 4.94–5.09 秒 |
| small-text | 1.36–1.66 秒 | 12.78–13.33 秒 |
| dense | 5.22–5.48 秒 | 40.26–40.76 秒 |

识别阶段范围分别为：simple，v3 0.46–0.49s / Lite 4.37–4.49s；small-text，v3 0.86–1.20s / Lite 11.96–12.80s；dense，v3 4.79–5.04s / Lite 39.69–40.24s。json边界含路径请求、解码和返回；Lite为解码后的识别调用，略有利于Lite。

三图忽略空白后的内容均匹配预期。v3 会合并部分英文、数字之间的空格；此配置下 Lite small 三图包括空格均匹配。不能把几张合成图的结果推广为准确率结论。

## tiny 结果

同一组公平输入、同等主要检测设置。ORT 以官方 RapidOCR 3.10.0 Python API调用，模型已提前显式加载；Lite为原生C++程序。每个“配置/图片”新进程加载后连续识别两次，下面是两次范围，不是多次独立启动的统计区间。

| 输入 | ORT + v6 small | ORT + v6 tiny | 原生 Lite + v6 tiny |
|---|---:|---:|---:|
| simple | 0.56–0.73 秒 | 0.20–0.42 秒 | 1.51–1.55 秒 |
| small-text | 1.16–1.46 秒 | 0.46–0.59 秒 | 3.16–3.58 秒 |
| dense | 5.51–6.53 秒 | 1.65–1.86 秒 | 7.42–8.20 秒 |

另外单独补测原生 tiny 的启动到结果，每图一次：

- simple：2.51 秒（本次识别调用 2.16 秒）。
- small-text：5.00 秒（本次识别调用 4.73 秒）。
- dense：8.09 秒（本次识别调用 7.87 秒）。

这些单次启动数据与上述连续调用不是同一轮、同一负载，不能拼成重复测量区间。tiny内容忽略空白后正确，小字混排存在部分空格合并；simple和dense文本匹配。tiny明显改善速度和体积，但 Lite tiny 本机结果仍慢于此前 v3。ORT tiny 的纯识别较快，Python冷启动仍存在，未重新打包验证最终启动总时间。不能据此承诺未来C++ ORT封装的速度。

## 各轮测试摘要

| 轮次 | 条件与计时口径 |
|---|---|
| 初测六图 | Python ctypes调用a14 DLL，CPU默认8线程、SDK默认检测；官方RapidOCR对照为2线程；每图三次。ORT首调用包含模型加载。 |
| 初步原生部署 | C++程序对照Python发布包；每次启动新进程；简单图和空白图对齐参数，密集图用默认参数，不应混称同参数。 |
| 时间复测 | 同一简单图，两回合反向顺序；Lite每进程两次，比较8/2线程和对齐/默认检测设置；同时记录系统CPU占用。 |
| 原v3复测 | 旧应用参数为2线程、最长边2048、默认补白50；每图两进程、每进程三次；Python v6每图一次。 |
| v3与Lite small相同输入 | 相同PNG、相同检测尺寸和主要阈值；两回合新进程识别，反转引擎顺序。 |
| tiny与small对比 | ORT显式预加载模型，每个新进程连续识别两次；Lite tiny为独立原生程序。 |
| 原生tiny启动到结果 | 每张图新启动一次原生程序。 |

简单图的时间复测结果：当前Python v6包启动到退出为5.68–5.83秒，其中就绪后请求耗时2.53–2.54秒，包含首次模型加载。Lite参数对齐时，8线程识别20.40–24.37秒，2线程23.14–28.72秒；Lite默认检测设置、2线程为5.39–6.68秒。默认检测设置未放大图像，与对齐设置的输入工作量不同。

原v3应用配置复测的启动到首个结果：简单图1.09–1.33秒，小字图1.53–1.63秒，密集图5.57–6.10秒；同期Python v6包分别为6.15、6.41、10.24秒。这一轮比较的是实际应用配置，不能当成相同模型或相同前处理的引擎跑分。

另一次参数对齐探索在部分样本完成后主动停止，不作为完整统计证据。最初尝试让两程序读取同一PPM文件时，v3包无法解码，未取得有效计时；随后改为同一PNG。无效试验未计入结果。
